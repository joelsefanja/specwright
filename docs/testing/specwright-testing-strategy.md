# Specwright Testing Strategy

This strategy is adapted from the `filters-online-issue-413/backoffice` Specwright setup. The reusable parts are the Specwright BDD conventions, agent/skill architecture, Playwright project strategy, reporting mindset, and file-input/GitLab workflow. Angular-specific commands, app-specific credentials, auth storage, and generated issue artifacts are intentionally not copied.

## Test Layers

Specwright has two test layers.

### 1. Product Tests For This Repository

These tests validate Specwright itself.

- Desktop app: Electron + React + Playwright Electron tests.
- Renderer UI: screenshot-based E2E flows for workflow screens, modals, GitLab source flow, and run feedback.
- Contrast checks: token-level theme contrast validation.
- Build checks: package and monorepo builds.

Use these commands:

```bash
pnpm --filter @specwright/desktop build
pnpm --filter @specwright/desktop test:contrast
pnpm --filter @specwright/desktop test:e2e
pnpm --filter @specwright/desktop test:e2e tests/e2e/workflow-redesign-screenshots.spec.ts
pnpm build
```

### 2. Generated BDD Tests In Target Projects

These tests are generated by Specwright for a user's app.

- Gherkin `.feature` files are compiled by `bddgen`.
- Step definitions import from `e2e-tests/playwright/fixtures.js`.
- Modules live under `e2e-tests/features/playwright-bdd/@Modules/`.
- Cross-feature workflows live under `e2e-tests/features/playwright-bdd/@Workflows/`.
- Shared steps live under `e2e-tests/features/playwright-bdd/shared/`.

Use target-project scripts such as:

```bash
pnpm test:bdd
pnpm test:bdd:auth
pnpm test:bdd:workflows
pnpm report:playwright
pnpm report:bdd
```

Important: target BDD tests must run `bddgen` before Playwright. Do not run plain `npx playwright test` against stale `.features-gen/` output.

## Backoffice Strategy We Are Reusing

The backoffice project has a mature Specwright setup with these useful patterns.

### Playwright Project Routing

Reusable routing pattern:

- `setup`: creates auth state when auth is enabled.
- `auth-tests`: tests login/logout with clean state.
- `serial-execution`: runs `@serial-execution` features with one worker and browser reuse.
- `precondition`: runs workflow setup features tagged `@precondition`.
- `workflow-consumers`: runs `@workflow-consumer` features after preconditions.
- `run-workflow`: optional single workflow lane.
- `chromium`: seed-file compatibility lane for generated exploration tests.
- `main-e2e`: default parallel module tests.

This pattern belongs in target projects generated by the Specwright plugin, not in the desktop Electron test config.

### Reporting

Reusable reporting mindset:

- Store E2E artifacts under `test-results/`.
- Keep Playwright HTML reports for debugging traces, screenshots, videos, and timing.
- Keep BDD/cucumber reports for functional review by module, workflow, feature, and scenario.
- Keep Allure where a target project wants combined reports across multiple test types.

For this repository, desktop artifacts are stored in `apps/desktop/test-results/`.

### BDD Structure

Reusable structure:

```text
e2e-tests/features/playwright-bdd/
  @Modules/
    @FeatureName/
      feature-name.feature
      steps.js
  @Workflows/
    @WorkflowName/
      @0-Precondition/
      @1-Verify/
  shared/
    auth.steps.js
    navigation.steps.js
    common.steps.js
```

Rules:

- Feature files describe behavior only.
- Co-located steps are scoped by `@` directory path.
- Reusable steps must live in `shared/`.
- Step files import from `fixtures.js`, not directly from `playwright-bdd`.
- Lowercase tags generated from module names.
- Use `@serial-execution` only when scenarios share state.

### Data Strategy

Reusable data persistence pattern:

1. Scenario-scoped page data.
2. In-memory feature data cache.
3. File-backed scoped JSON data for cross-feature or worker-safe persistence.

Reusable Gherkin data table format:

```gherkin
| Field Name | Value           | Type            |
| Name       | <gen_test_data> | SharedGenerated |
| Email      | <from_test_data> | SharedGenerated |
```

`<gen_test_data>` generates and caches data. `<from_test_data>` reads previously stored data.

### Agent And Skill Strategy

Reusable `.claude` strategy:

- Skills orchestrate workflows.
- Agents are pure single-responsibility building blocks.
- Agent memory stores learned selectors and fixes.
- Rules document BDD conventions, debugging gotchas, and architecture decisions.

The copied `.claude/` folder in this repository is intended to preserve this strategy for Specwright-generated target tests while being adapted for the Electron/React desktop stack.

## What We Do Not Copy From Backoffice

Do not copy these into this repository:

- `e2e-tests/.env.testing` because it can contain local credentials.
- `e2e-tests/playwright/auth-storage/.auth/user.json` because it contains auth session state.
- generated GitLab issue markdown/json files as committed product fixtures unless explicitly needed.
- Angular-specific package scripts or build config.
- backoffice-specific selectors, page objects, or helper names unless used as examples only.

## Self-Test Plan For Specwright Desktop

The main self-test should use `SPECWRIGHT_README_FOR_TESTING.md` as a file source in the desktop app.

Target flow:

1. Launch Specwright Desktop with Playwright Electron.
2. Set language to English for stable selectors.
3. Select or inject a temporary project folder.
4. Capture screenshot: choose project folder step.
5. Set app URL.
6. Capture screenshot: app access step.
7. Open scenario source selection.
8. Select file source.
9. Mock the native file picker to return `SPECWRIGHT_README_FOR_TESTING.md`.
10. Let the real upload route copy the file into the project.
11. Capture screenshot: file source selected and preview available.
12. Continue to review.
13. Capture screenshot: review and start step with the README source.
14. Assert that the review explains visible progress and enables start when setup is complete.
15. Record Playwright video for the full test.

Important assertions:

- The file source card is usable.
- The selected README file is visible in the scenario card.
- Review uses the README file as source context.
- The run step explains progress before start.
- No external terminal window should be needed for the UI test.

## Desktop E2E Artifact Policy

For UI review tests:

- Save one screenshot per major step.
- Save video for the full flow when requested.
- Put deterministic galleries under `apps/desktop/test-results/<flow-name>/`.
- Let Playwright retain trace/video artifacts under its normal `test-results` output.

Recommended new test name:

```text
apps/desktop/tests/e2e/specwright-readme-file-flow.spec.ts
```

Recommended artifact directory:

```text
apps/desktop/test-results/specwright-readme-file-flow/
```

## Verification Rules

Before treating a UI/testing strategy change as complete, run:

```bash
pnpm --filter @specwright/desktop build
pnpm --filter @specwright/desktop test:contrast
pnpm --filter @specwright/desktop test:e2e tests/e2e/specwright-readme-file-flow.spec.ts
```

If only `.claude` or docs changed, a build is optional, but the relevant files must still be reviewed for project-specific assumptions.
